## How to use this plan

- The work is split into **phases** (spec §9), each split into **chunks**. A chunk fits one
  focused Claude Code session and ends with code that builds, passes tests and runs.
- Each phase ends with a **phase gate** (Part D).
- Tick checkboxes as chunks land. If a chunk turns out too big, split it here first.
- A chunk marked `needs Q-x` waits until that question is decided in `DECISIONS.md`.

## Part A. Architecture baseline (confirm before Phase 1)

### A.1 Repository layout

```
ShoppingCart/
├── Cargo.toml              # workspace
├── crates/
│   ├── domain/             # pure logic, no IO: fractional index, amount parsing,
│   │                       # catalogue ranking,
│   │                       # name normalisation, visibility rules, Mealie mapping
│   └── server/             # Axum binary: config, API, auth, SSE, jobs, DB, embeds web/dist
├── migrations/             # sqlx migrations (SQLite)
├── web/                    # Svelte 5 + Vite SPA
│   └── src/lib/api/types/  # TS types generated by ts-rs (committed)
├── docs/                   # MkDocs site + SPEC/WORKPLAN/DECISIONS
├── scripts/                # measure.sh, helpers
├── Dockerfile              # node build → rust musl build → scratch
├── docker-compose.yml
├── mkdocs.yml
└── Makefile                # dev-server, dev-web, test, check, types, build, up, measure, docs
```

### A.2 Request flow

Browser/API client → Axum router (`/api/v1/*`, static files fallback to `index.html`) →
auth extractor (cookie or bearer, scope check) → handler → `visibility` module (all permission
SQL) → SQLite (WAL, one writer pool of 1, reader pool) → event log row → SSE broadcaster
(per-subscriber visibility filter).

### A.3 Conventions

- ULIDs as `TEXT`; timestamps as RFC 3339 UTC `TEXT`; `rev` from a single `revs` counter row
  bumped inside the write transaction.
- Soft delete with `deleted_at`; a daily job purges tombstones older than 30 days.
- Positions: fractional-index strings (`domain::order`).
- Errors: `Problem` (RFC 9457) with stable `type` slugs.
- Every handler that touches shared data takes a `Viewer` (user id, scope) and calls
  `visibility::*`; code review rejects ad-hoc permission checks.

## Part C. Open questions (proposed defaults)

| Q | Question | Proposed default | Blocks |
|---|---|---|---|
| Q-1 | What happens to ticked items? | Move to *In the cart* at the bottom; **Finish shopping** removes them (undo for 10 s). No automatic clearing. | 2.2 |
| Q-2 | Can a list viewer tick items? | No: viewer is read only; give *editor* to someone who shops with you. | 4.3 |
| Q-3 | Own wishlist default visibility | Private; one tap to share with a household. | 5.1 |
| Q-4 | Who sees a claim on a gift list? | Everyone who can see the gift list (except the recipient), with the claimer's name. | 5.3 |
| Q-5 | Mealie: after import, tick or delete in Mealie? | Tick (checked), so Mealie's history keeps it. Configurable. | 6.3 |
| Q-6 | UI language | English only in v1; strings centralised so Estonian can follow. | 1.4 |
| Q-7 | Currency for wish prices | Per-user setting, default EUR. | 5.1 |
| Q-8 | Self-sign-up / invite links | No: admin creates users. Invite links maybe later. | 1.3 |
| Q-9 | Catalogue per user or per household? | Per user; an optional "share my catalogue with household X" can come later. | 2.3 |
| Q-10 | Picture source | Open Food Facts lookup (on by default, can be switched off) plus own photos/uploads. Products and pictures are per user like the catalogue; people on a shared list see the pictures of the items on it. | 3b.3 |
